# Factory jobs

Factory jobs run a frozen source tree and acceptance suite inside a disposable,
offline VM and keep the evidence on the host. The daemon journals every
submission before it answers, runs the job with pinned images and resources,
captures output and artifacts, destroys the VM and keeps the record until its
retention expires. Guest deletion cannot remove host evidence.

The API is experimental and versioned (`contract_version: 1`). Execution is
disabled by default.

## Enable execution

A daemon runs factory jobs only with `factory_jobs_enabled = true`, an explicit
resource budget, a nonempty bearer token and a nonempty `exec_allowlist`.
Startup rejects enablement without a valid budget before creating any daemon
resources.

```toml
factory_jobs_enabled = true

[factory_resource_budget]
max_jobs = 2
max_vcpus = 4
max_memory_mib = 9216
memory_overhead_mib = 512
max_root_disk_bytes = 17179869184
max_boot_storage_bytes = 42949672960
min_free_storage_bytes = 17179869184
```

The budget is an allocation ceiling chosen by the operator, not detected host
capacity. Leave room for the host itself and for non-factory VMs, image caches
and retained evidence. Admission charges each job against it:

| Budget | Charge per job |
| --- | --- |
| `max_jobs` | One slot |
| `max_vcpus` | Requested vCPUs |
| `max_memory_mib` | Requested guest memory plus `memory_overhead_mib` |
| `max_root_disk_bytes` | Requested root disk size |
| `max_boot_storage_bytes` | Twice the root disk size, plus 256 MiB kernel, 512 MiB initrd and 8 MiB serial log bounds |

Boot storage is charged in full even when the root copies start sparse or
reflinked, because both can grow to their full size. Fresh admission also
measures available space in the data and state directories. It requires
`min_free_storage_bytes` plus all pending boot reservations plus 64 MiB of
journal headroom per retained receipt, combining the charges when both
directories share a filesystem. A missing or unreadable directory, a failed
measurement or an arithmetic overflow rejects admission.

Charges are checked atomically at acceptance, survive daemon restarts and are
released only after cleanup of the job's VM and files is confirmed. A rejected
fresh request receives HTTP 429 and creates no receipt. Independently of the
budget, a daemon holds at most 16 active or cleanup-pending jobs.

## Authentication and trust

Every factory route requires the configured bearer token, including over
loopback. Without a token the routes fail closed even when execution is
enabled. Every supplied environment key must appear in `exec_env_allowlist`;
an empty list permits none.

The allowlists check executables, not arguments. The caller must supply trusted,
operator-configured argv arrays, never commands generated by a model. One token
represents one administrative trust domain; it is not a per-tenant boundary.
Never put credentials in archives, environment values or correlation fields.

## Prepare the inputs

Each archive must be a canonical frozen tar produced by `husker bundle freeze`.
An arbitrary tar is rejected.

```sh
husker bundle freeze ./src ../source.tar
husker bundle freeze ./acceptance ../acceptance.tar
husker bundle verify ../source.tar --digest sha256:<hex> --size <bytes>
```

`freeze` prints the bundle's `version`, `digest`, `size_bytes` and
`file_count`; record that identity in the execution specification. The
destination must be a new file outside the source tree. `verify` checks the
complete digest and byte count before anything is decoded. Both commands run
locally and refuse `--api-url` or `--context`.

The format is uncompressed canonical USTAR: regular files only, sorted by path,
with modes normalized to 0644 or 0755 and owners and timestamps zeroed. Freezing
unchanged bytes always yields the same digest. Links, special files, PAX or GNU
extensions, duplicate paths and trailing data are rejected. Empty directories
are omitted.

Capture skips common credential and configuration paths: `.git`, `.ssh`, `.aws`,
`.azure`, `.config`, `.codex`, `.claude`, `.gnupg`, `.kube`, `.docker`, `.env`
and `.env.*`, `.netrc`, `.npmrc`, `.pypirc`, `.gitconfig`, `.git-credentials`,
`credentials.json` and `auth.json`. This is a denylist, not a secret scanner:
review the inputs, because credentials stored under other names are included.

## Submit a job

`POST /v1/jobs` accepts:

```json
{
  "submission": {
    "idempotency_key": "non-secret-stage-round-key",
    "execution_specification_digest": "sha256:<canonical-specification-hash>",
    "specification": { "version": 1 }
  },
  "source_bundle": "<base64 frozen source tar>",
  "acceptance_bundle": "<base64 frozen acceptance tar>",
  "retention_until": "2026-10-08T12:00:00Z"
}
```

The specification above is abbreviated. The daemon's `/api-docs/openapi.json`
documents the complete schema: image identities, bundle digests and sizes,
commands, numeric user identity, resources, network, deadline, writable paths,
artifacts and correlation. The specification digest is the SHA-256 of the
specification serialized as compact UTF-8 JSON with recursively sorted keys.
Deadlines are UTC with whole seconds. `network.mode` must be `"none"`.

| Limit | Value |
| --- | --- |
| Archive size (decoded) | 32 MiB, at most 8192 files |
| Specification | 64 KiB, at most 32 commands |
| Artifacts | 16 per job, 4 MiB each, 16 MiB total |
| Captured output | 4 MiB, at most 4096 events |
| Result manifest | 64 KiB |
| Retention | After the deadline, at most 30 days ahead |
| Retained jobs | 64 with evidence, including terminal ones until deletion or expiry |
| Submission receipts | 4096, counting retained jobs and tombstones whose deadline is still ahead |

The default HTTP body limit of 2 MiB fits only small submissions. Set
`api_max_request_bytes` to accept larger ones; 90 MiB fits two maximum-sized
archives and a maximum specification after base64 encoding.

Responses:

| Status | Meaning |
| --- | --- |
| 202 | New receipt, `replayed: false`. Acceptance is durable before the response. |
| 200 | Identical key and specification already accepted, `replayed: true`. Nothing runs again. |
| 409 | The key is known with a different specification digest. |
| 429 | Budget, retained-job or receipt capacity exhausted. No receipt is created. |

An accepted job can already have failed by the time it is inspected, for
example when no worker slot is available. The receipt then records the failure
without executing anything.

### Lost responses

Journal the idempotency key, the specification digest and the frozen request
before calling the API. If the response is lost, look the job up with a
read-only request, or replay the identical request. Never resolve uncertainty
with a fresh key: a timed-out observation is not a terminal result, and a new
key runs the work again.

## Observe and collect evidence

Evidence references in responses are relative and never contain the token.

- `GET /v1/job-submissions?idempotency_key=K&execution_specification_digest=D`:
  find a job after a lost receipt. Returns the inspection for a known identity,
  404 for a key this journal has never seen, and 409 for a different digest or
  deleted evidence. It never starts work. A 404 does not prove the work never
  ran on another daemon or against a lost database.
- `GET /v1/jobs/{id}`: status, session and VM identity, collection status,
  result manifest, cleanup receipts and artifact descriptors. The manifest and
  specification are bounded JSON strings; parse them as data.
- `GET /v1/jobs/{id}/events?after=N`: up to 128 events with base64 data, the next
  cursor, `has_more` and an explicit output-truncation flag. Events can hold
  arbitrary binary stdout and stderr. A page can be empty yet still advance the
  cursor over truncated output.
- `GET /v1/jobs/{id}/artifacts`: retained artifact descriptors.
- `GET /v1/jobs/{id}/artifacts/{index}`: one descriptor with its base64 bytes.
  Check the digest and length before using it.

The outcome and the collection status are separate facts. A job counts as
passing only when the outcome is `completed`, collection succeeded, the manifest
validates and every required artifact is present. An unknown outcome, an
infrastructure failure, a timeout, a cancellation or incomplete collection
never counts as passing.

## Cancel and delete

`POST /v1/jobs/{id}/cancel` persists a cancellation decision. It returns 202
while cleanup is still pending and 200 once cleanup is confirmed, with the job
inspection in both cases. The first terminal decision wins: cancelling a job
that already completed returns the completed outcome. Cancellation keeps the output captured so far and
marks collection failed when the final tail is unavailable. A VM created while
cancellation was in flight still belongs to the job and is cleaned up with it.

Acknowledged cancellation does not mean the VM is gone. Inspect the job until
`cleanup_pending` is false. Cleanup destroys only the exact VM generation bound
to the job, and it releases files and the vsock CID only after the VMM confirms
destruction, or confirms that allocation never reached the VMM. A "not found"
answer or a failed observation leaves cleanup pending, and the retry loop tries
again.

`DELETE /v1/jobs/{id}` returns 204 for a terminal job whose cleanup is
confirmed, and 409 while it is running or cleanup is pending. Deletion removes
the evidence but keeps a submission tombstone, so replaying the key before the
job's deadline is refused with 409 and cannot run the work again. Evidence also
expires automatically after `retention_until`, once cleanup is confirmed.

A tombstone is dropped once its deadline has passed. From then on the key is
unknown to the journal: a lookup returns 404, and an identical replay is
refused because its deadline is no longer in the future. Neither path can run
the work again.

## Restart and shutdown

On shutdown the daemon stops accepting factory jobs immediately. Requests after
that point receive a capacity error; resubmit the same key to the next daemon
run. Unfinished jobs are sealed before the general VM drain, and the daemon
waits up to 15 seconds for job workers. A worker that outlives the grace period
stays registered and is reported, never silently abandoned.

On startup, before serving HTTP, the daemon seals every unfinished job without
re-executing it:

| Previous state | Recorded outcome |
| --- | --- |
| Accepted, deadline in the future | Interrupted |
| Preparing or running, deadline in the future | Unknown |
| Any unfinished state, deadline passed | Timed out |
| Terminal | Unchanged |

Output already journaled stays available, and collection is recorded as failed.
A guest result staged before the interruption is kept in the failure envelope,
or recorded by digest with `guest_result_body_truncated: true` when it exceeds
the manifest limit. It is diagnostic only and never turns the outcome into a
pass. Running the work again needs a new submission with a new key.

## Guest isolation

A factory VM has no network device: on Apple VZ, `network: none` omits the
virtual NIC entirely, so nothing inside the guest can restore connectivity. The
guest agent stays reachable over vsock and accepts connections only from the
host CID, rejecting guest-local peers before parsing any request. No host
directories are shared into the guest.

Inside the guest, the job runner drops to the specification's UID and GID (at
least 1000) with no capabilities and `no_new_privs`, and refuses to run without
a cgroup v2 `pids` controller and `cgroup.kill`. Frozen source and acceptance
trees are read-only. Only the specification's `writable_directories` (at most
16, initially empty) and `/tmp` are writable. Each command runs under a process
ceiling and a timeout of at most 20 minutes, and leftover child processes are
killed after every command. If termination cannot be confirmed, evidence
collection fails and the host destroys the VM.

A separate guest kernel is not an authorization boundary for hostile tenants.
Code loaded by the acceptance suite runs in the same guest as the code under
test.

## Python client

`husker.Client` implements this contract and does not start a daemon.

```python
from husker import Client

client = Client("http://127.0.0.1:7777", token=daemon_token)

# Journal the key, digest and frozen inputs before this call.
job = client.submit_job(submission, source_tar, acceptance_tar,
                        retention_until="2026-10-08T12:00:00Z")

# After a lost response, look the job up without starting work:
# job = client.find_job(submission["idempotency_key"],
#                       submission["execution_specification_digest"])

snapshot = job.wait(timeout=60, cleanup=True)

# A wait timeout leaves the job running. Reconnect with the journaled UUID:
job = client.job(job.id,
                 specification_digest=submission["execution_specification_digest"])
page = job.events(after=last_committed_cursor)
for event in page.events:
    persist_event(event.sequence, event.stream, event.data)
# Persist page.next_cursor only after the events are committed.

artifact = job.artifact(0)  # Verifies descriptor, length and SHA-256.
```

`submit_job` validates the archive and specification hashes locally before
sending them; the server still decides whether they are allowed. The client
performs no automatic retries and has no fallback execution path. Durable
journaling is the caller's responsibility.

A `JobSnapshot` exposes `record`, `artifacts`, `references`, `terminal` and
`cleanup_pending`. `wait(cleanup=True)` returns only once the job is terminal
and its cleanup is confirmed. `job.cancel()` returns a snapshot instead of
assuming termination, and `job.remove()` goes through the server's deletion
guard. The client verifies the job UUID and, when supplied, the specification
digest on every observation. It rejects unsupported contract versions, malformed
cursor pages and references to other hosts, and bounds every response read. The
token travels only in the `Authorization` header.

## Limitations

- Only offline jobs (`network.mode = "none"`) are supported.
- A VMM creation call that never returns leaves cleanup pending, even after
  the deadline or a cancellation decision.
- Cleanup confirmation that was not yet journaled when the daemon died is lost.
  After restart the allocation stays pending until it is proven safe again.
- Storage checks are point-in-time measurements. They do not reserve space
  against other processes on the host.

## Tests

These suites run without launching a VM:

```sh
cargo test -p husker-api --test jobs --test openapi_contract --no-default-features
cargo test -p husker-core --lib job_worker --no-default-features
cargo test -p husker-core --test job_spec --no-default-features
python3 -m unittest discover -s tests -p 'test_sdk.py'
```

`tests/fixtures/job_spec_v1.json` is shared by the Rust and Python suites to
keep the canonical specification digest identical in both, including Unicode,
quotes, backslashes and newlines in arguments.

Live probes run only when explicitly enabled and only against an isolated test
daemon. `scripts/ci/agent_peer_e2e.py` (`HUSKER_RUN_AGENT_PEER_E2E=1`) checks
that a guest process cannot reach its own agent over vsock.
`scripts/ci/factory_boundary_e2e.py` and `scripts/ci/factory_lifecycle_e2e.py`
exercise the offline boundary, and command failure, timeout and cancellation
with escaping child processes.
